# Open Ontologies engine chart (draft)

Runs one engine with persistent storage, an internal-only HTTP MCP service and bearer authentication. This chart is a draft: it has not been rendered with Helm, run in a cluster, or tested against the published container image. Verify the upstream image tag and container entrypoint before use. It intentionally does not expose an ingress; add authenticated TLS access appropriate to your environment before connecting external agents. A token alone does not encrypt traffic. Restrict network access and use least-privilege tools for agents.

Create a namespace and a Secret named by `auth.existingSecret` containing a nonempty `token` key. Avoid putting secrets in Helm values, shell history or source control. Install with `helm upgrade --install ontology ./helm/open-ontologies -n YOUR_NAMESPACE --set auth.existingSecret=YOUR_SECRET`. The service will be `ontology-engine:8080`; MCP is at `/mcp` and health at `/health`. Use `kubectl port-forward service/ontology-engine 8080:8080` to access locally and provide the bearer token in the MCP client. Confirm initialization and query behavior with your MCP client.

A single StatefulSet replica avoids concurrent access to one local store. Its PVC persists across pod restarts and is not automatically deleted when the release is uninstalled; plan backups and restore tests. This is not a high-availability design. The chart does not automatically load the example ontology; load and validate the supplied Turtle data explicitly using the engine tools. Configure storage class and resources in values.yaml. Validate security, startup behavior, token handling and backup/restore in your cluster before production use.
